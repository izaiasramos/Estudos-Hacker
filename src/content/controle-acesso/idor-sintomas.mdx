Na revisão da rota de pedidos, pergunte de onde vêm os dois valores decisivos: o identificador do pedido e a identidade autorizada. Na versão vulnerável, só o primeiro aparece.

<Code caption={"Consulta que confia no identificador"}>

```
const pedido = await db.one(
  "SELECT * FROM pedidos WHERE id = ?",
  [params.id],
);
return pedido;
```

</Code>

O parâmetro `?` ajuda a evitar injeção de Structured Query Language (SQL), a linguagem de consulta do banco, mas não cria autorização. O contraste está no filtro de dono:

<Code caption={"Consulta que exige o dono da sessão"}>

```
const pedido = await db.one(
  "SELECT * FROM pedidos WHERE id = ? AND user_id = ?",
  [params.id, sessao.userId],
);
if (!pedido) return notFound();
return pedido;
```

</Code>

O `user_id` vem da sessão emitida e verificada pelo servidor, nunca do corpo, da query ou de um campo escondido. Para um recurso alheio, a equipe decide entre 403 (proibido) e 404 (não encontrado, sem confirmar existência), sempre sem devolver o conteúdo.

Síntese: identificação sem filtro de recurso ainda é acesso quebrado.
