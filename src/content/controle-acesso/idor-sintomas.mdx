Na revisão da rota de pedidos, pergunte de onde vêm os dois valores que decidem tudo: **o identificador do pedido** e **a identidade de quem pede**. Na versão vulnerável, só o primeiro aparece.

<Code caption={"Consulta que confia no identificador"}>
```js
const pedido = await db.one(
  "SELECT pedido_id, nome_do_item, situacao_do_pedido FROM pedidos WHERE pedido_id = ?",
  [params.pedidoId],
);
return pedido;
```
</Code>

Nesta consulta, `pedido_id` é a coluna que identifica o pedido. `params.pedidoId` é o número retirado do endereço, como o `103` de `/pedidos/103`. O `?` protege contra injeção de SQL, mas não cria autorização. A diferença está no segundo filtro:

<Code caption={"Consulta que exige o dono da sessão"}>
```js
const pedido = await db.one(
  "SELECT pedido_id, nome_do_item, situacao_do_pedido FROM pedidos WHERE pedido_id = ? AND proprietario_usuario_id = ?",
  [params.pedidoId, sessao.usuarioId],
);
if (!pedido) return notFound();
return pedido;
```
</Code>

    { key: "valor", label: "Valor usado" },

/>

O `proprietario_usuario_id` é a coluna que guarda quem é dono do pedido. `params.pedidoId` veio do endereço; `sessao.usuarioId` veio da sessão que o servidor emitiu e verificou, nunca do corpo do pedido, da URL ou de um campo escondido. Para um recurso de outra pessoa, a equipe escolhe entre **403** (proibido) e **404** (não encontrado, sem confirmar que existe). Em ambos os casos, nunca devolve o conteúdo.

**Em resumo:** identificar quem pede, sem filtrar o recurso, ainda é acesso quebrado.

## Mão na massa: leia o pedido de outra pessoa

**Onde se faz isso?** Num servidor seu, pelo navegador ou pelo `curl`. Aqui, finja que a Alice é a pessoa logada. Precisa do Node.js 22.5 ou mais novo (`node -v` mostra a versão). Tudo roda **só na sua máquina**, em arquivos que você mesmo cria.

<Code caption="idor.mjs: uma rota de pedidos que só olha o id">
```js
import { createServer } from "node:http";

const pedidos = [
  { pedidoId: 101, proprietario: "alice", nomeDoItem: "Margherita" },
  { pedidoId: 102, proprietario: "alice", nomeDoItem: "Suco" },
  { pedidoId: 103, proprietario: "bruno", nomeDoItem: "Calabresa" },
];

createServer((req, res) => {
  const usuarioLogado = "alice"; // finja que isso veio de uma sessão válida
  const pedidoId = Number(req.url.split("/").pop());

  // INSEGURO: acha pelo id e entrega
  const pedido = pedidos.find((pedido) => pedido.pedidoId === pedidoId);

  // SEGURO: troque a linha acima por esta
  // const pedido = pedidos.find((pedido) =>
  pedido.pedidoId === pedidoId && pedido.proprietario === usuarioLogado
);

  if (!pedido) { res.statusCode = 404; return res.end("não encontrado"); }
  res.end(JSON.stringify(pedido));
}).listen(4000, () => console.log("http://localhost:4000/pedidos/101"));
```
</Code>

**Passo a passo:**

1. Rode `node idor.mjs`.
2. Abra `http://localhost:4000/pedidos/101`. É o pedido da Alice. Tudo certo.
3. Troque o número na barra de endereços para `103`. Aparece o pedido do **Bruno**, mesmo você sendo a Alice.

**Agora conserte:** comente a linha "INSEGURO" e descomente a linha "SEGURO". Reinicie o servidor e repita. O `/pedidos/103` passa a responder `não encontrado`, e o `101` continua funcionando.

**O que observar:** a diferença é um `&& pedido.proprietario === usuarioLogado`. Um filtro de proprietário, vindo da sessão, é o que separa um app seguro de um vazamento.
