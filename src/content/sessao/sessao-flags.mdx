Agora compare duas chaves. A primeira pode ser lida por scripts, viajar fora de HTTPS e acompanhar pedidos iniciados por outro site. A segunda recebe três atributos — instruções no cookie — que reduzem esses caminhos.

<Glossary term={"HttpOnly"} text={"Atributo que impede o JavaScript da página de ler o cookie. O navegador ainda pode enviá-lo automaticamente ao servidor."} />

<Glossary term={"Secure"} text={"Atributo que manda o navegador enviar o cookie somente por conexão HTTPS. Ele não cria HTTPS; o site também precisa estar configurado para usá-lo."} />

<Glossary term={"SameSite"} text={"Atributo que limita quando o cookie acompanha um pedido iniciado em outro site. Strict é mais restritivo; Lax permite alguns casos, como certas navegações comuns; None permite envio entre sites e normalmente exige Secure."} />

<Code caption={"Contraste de configuração"}>

```
frágil:   sessao=chave
melhor:   sessao=chave; HttpOnly; Secure; SameSite=Lax
```

</Code>

Esses atributos não resolvem todo o ciclo. No login, o servidor deve gerar uma chave nova e invalidar a anterior. No logout, deve invalidar a chave atual. Um prazo de expiração limita sessões esquecidas.

<Callout tone="dev">

Decisão para este cenário: use HttpOnly, Secure e SameSite=Lax como base; escolha Strict quando o fluxo aceitar uma política mais restritiva. Só use None quando o produto realmente precisar de envio entre sites e houver proteção adequada para esse fluxo.

</Callout>
