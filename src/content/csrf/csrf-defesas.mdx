O endpoint de transferência precisa reconhecer mais do que a sessão. Quatro decisões se complementam.

**1. Token anti-CSRF.** É um valor imprevisível ligado à sessão ou ao formulário. O aplicativo legítimo o inclui no envio, e o servidor confere. Um site de fora pode até mandar um formulário, mas normalmente não consegue ler o token da página legítima para copiá-lo.

**2. SameSite.** É um atributo do cookie que controla se ele viaja em pedidos vindos de outros sites. Atenção: **site** não é o mesmo que **origem**. Na prática, site considera o protocolo e o domínio principal, ignorando a porta. Então `https://app.exemplo.com` e `https://painel.exemplo.com` são origens diferentes, mas o mesmo site. O SameSite não separa esses dois, mas um token ou a conferência de Origin separam.

- `Strict`: o mais fechado.
- `Lax`: permite alguns fluxos de navegação, mas bloqueia o cookie em muitos pedidos de outros sites, como um `POST` de formulário externo.
- `None`: permite envio entre sites e exige `Secure`.

Escolha pensando nos fluxos legítimos do seu produto.

**3. Origin e Referer.** São cabeçalhos que dizem de onde o pedido partiu. `Origin` informa a origem. `Referer` costuma informar a página anterior. Compare com uma lista exata de origens permitidas. Não aceite só porque o texto "contém" o seu domínio. Decida também o que fazer quando o cabeçalho não vier.

**4. GET e POST.** O GET deve apenas ler. O POST envia uma ação que muda estado. Mover a mutação para POST evita disparos por um simples link ou imagem, mas **POST sozinho não impede CSRF**: um site externo também consegue enviar formulários POST.

## Mão na massa: feche a transferência

Salve como `csrf-seguro.mjs`. É o mesmo banco, agora com as camadas desta unidade: cookie `SameSite=Strict`, só aceita `POST`, confere o cabeçalho `Origin` e exige um token de uso único.

<Code caption="csrf-seguro.mjs: banco com defesas em camadas">
```js
import { createServer } from "node:http";
import { randomBytes } from "node:crypto";

let saldo = 1000;
const tokens = new Set();

createServer((req, res) => {
  const url = new URL(req.url, "http://localhost:4000");
  const logado = (req.headers.cookie ?? "").includes("sessao=alice");

  if (url.pathname === "/entrar") {
    res.setHeader("Set-Cookie", "sessao=alice; HttpOnly; SameSite=Strict; Path=/");
    return res.end("Logada. Saldo: " + saldo);
  }
  // A página legítima pega um token e o envia junto com o POST
  if (url.pathname === "/token" && logado) {
    const token = randomBytes(16).toString("hex");
    tokens.add(token);
    return res.end(token);
  }
  if (url.pathname === "/transferir") {
    const origemOk = req.headers.origin === "http://localhost:4000";
    const token = url.searchParams.get("token");
    if (req.method !== "POST" || !logado || !origemOk || !tokens.delete(token)) {
      res.statusCode = 403;
      return res.end("Recusado");
    }
    saldo -= Number(url.searchParams.get("valor"));
    return res.end("Transferido! Saldo: " + saldo);
  }
  res.end("Saldo: " + saldo);
}).listen(4000);
```
</Code>

**Teste pelo terminal** (com o servidor rodando, num segundo terminal):

```bash
curl -s -c cookies.txt http://localhost:4000/entrar
# Pedido forjado, como o do site de fora: GET, sem token
curl -s -b cookies.txt "http://localhost:4000/transferir?valor=500"
# Pedido legítimo: pega o token e envia por POST com a Origin certa
TOKEN=$(curl -s -b cookies.txt http://localhost:4000/token)
curl -s -b cookies.txt -X POST -H "Origin: http://localhost:4000" \
  "http://localhost:4000/transferir?valor=100&token=$TOKEN"
```

O primeiro pedido volta `Recusado`. O segundo volta `Transferido! Saldo: 900`.

**Seu desafio:** tente repetir o segundo pedido com o mesmo token. Ele já foi usado, então deve ser recusado.
