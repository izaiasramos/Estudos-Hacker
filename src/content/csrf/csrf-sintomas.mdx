Você abre o endpoint fictício e encontra isto:

<Code caption={"Mutação exposta como leitura"}>
```http
GET /transferir?valor=100&para=destino
Cookie: sessao=...
```
</Code>

**Primeiro sinal: uma leitura que muda estado.** Um GET está fazendo uma transferência. Isso pode ser disparado por um link, uma navegação ou um recurso carregado. Passar para POST reduz o problema, mas ainda é preciso olhar as outras camadas.

**Segundo sinal: formulário sem token anti-CSRF.** É uma lacuna, mas não prova sozinha que o ataque funciona. Um cookie `SameSite=Strict`, por exemplo, pode impedir que a sessão acompanhe o pedido de outro site. E uma validação correta de Origin pode recusar o envio antes da mutação.

**Terceiro sinal: aceitar qualquer Origin ou confiar cegamente no Referer.** O servidor deve comparar a origem recebida com a esperada. Se a infraestrutura remove cabeçalhos ou há fluxos legítimos entre origens, a política precisa prever isso sem "abrir tudo".

<Callout tone="armadilha">
Não transforme checklist em teorema. "Faltou uma caixa, logo há ataque" é tão impreciso quanto "tem uma caixa, logo está seguro". Trace o pedido inteiro: de onde veio, qual cookie levou, qual método usou, se tinha token, qual origem declarou e quem estava autorizado.
</Callout>

Uma boa revisão termina com uma frase específica: qual pedido o atacante consegue montar, quais credenciais o navegador anexa e em qual validação ele seria aceito ou recusado.

## Mão na massa: faça uma transferência sem a Alice querer

**Onde se faz isso?** Você vai rodar dois sites na sua máquina: um banco vulnerável e uma página "de outro dono". Precisa do Node.js 22.5 ou mais novo (`node -v` mostra a versão). Tudo roda **só na sua máquina**, em arquivos que você mesmo cria.

<Code caption="csrf.mjs: banco vulnerável (porta 4000) e site de fora (porta 4001)">
```js
import { createServer } from "node:http";

let saldo = 1000;

// Banco vulnerável (porta 4000): a transferência é um GET e só olha o cookie
createServer((req, res) => {
  const url = new URL(req.url, "http://localhost:4000");
  const logado = (req.headers.cookie ?? "").includes("sessao=alice");
  if (url.pathname === "/entrar") {
    res.setHeader("Set-Cookie", "sessao=alice; HttpOnly; Path=/");
    return res.end("Logada como Alice. Saldo: " + saldo);
  }
  if (url.pathname === "/transferir" && logado) {
    saldo -= Number(url.searchParams.get("valor"));
    return res.end("Transferido! Saldo: " + saldo);
  }
  res.end("Saldo: " + saldo);
}).listen(4000);

// Site "de outro dono" (porta 4001): dispara o pedido sem a Alice perceber
createServer((req, res) => {
  res.setHeader("Content-Type", "text/html");
  res.end(`<h1>Fotos de gatinhos</h1>
    <img src="http://localhost:4000/transferir?valor=500" width="1" height="1">`);
}).listen(4001);

console.log("1) abra http://localhost:4000/entrar");
console.log("2) abra http://localhost:4001 em outra aba");
console.log("3) volte em http://localhost:4000 e veja o saldo");
```
</Code>

**Passo a passo:**

1. Rode `node csrf.mjs`.
2. No navegador, abra `http://localhost:4000/entrar`. Você é a Alice e o saldo é 1000.
3. Em **outra aba**, abra `http://localhost:4001`. Parece uma página inocente de gatinhos.
4. Volte em `http://localhost:4000` e recarregue: o saldo é **500**. A imagem escondida mandou o navegador pedir `/transferir`, e ele anexou o cookie da Alice sozinho.

**O que observar:** a Alice não clicou em nada. O servidor só perguntou "o cookie é válido?", e nunca "foi ela quem pediu?".

<Callout tone="armadilha">
As portas 4000 e 4001 contam como o **mesmo site** para o navegador, porque o SameSite ignora a porta. Num cenário real os domínios seriam diferentes e o `SameSite=Lax` já barraria esse GET. Mesmo assim, uma ação que muda estado em GET é um erro de projeto.
</Callout>
